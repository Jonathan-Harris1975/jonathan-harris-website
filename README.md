# Jonathan Harris Online

This repository is the governed source and build system for **https://jonathan-harris.online**. Cloudflare Pages publishes the repository root, Cloudflare Pages Functions provide same-origin runtime routes, and two separately deployed Workers provide Agent Readiness and CogniPal rate limiting.

The project deliberately mixes static, generated and runtime-governed content. The build is therefore a release gate rather than a simple file copy: it imports the approved eBook workbook, rebuilds generated assets and routes, validates security and crawler contracts, exercises the Pages/Worker integration contracts, and rejects inconsistent generated output.

## Architecture and source boundaries

### Static and generated website

The repository contains the homepage, eBook catalogue and detail pages, topic/resource pages, newsletter/contact/contribution surfaces, shared CSS/JavaScript, images, crawler files, redirects and downloadable assets.

Key governed sources and generated outputs include:

- `jonathan-harris-site-url-inventory-remediated-release-ready.xlsx` — approved human-editable eBook workbook used by the canonical build.
- `data/ebooks-master.json` — generated in-repository eBook record used by pages and derivatives.
- `sitemap.xml`, `robots.txt`, `llms.txt`, `url-manifest.json`, `_redirects` and `_headers` — public crawler/routing/security assets validated by the build.
- `downloads/ai-glossary-cheat-sheet/ai-glossary-cheat-sheet.pdf` — deterministic PDF generated by `scripts/generate_ai_glossary_pdf.py`.
- `assets/` and generated HTML pages — browser-facing site assets published by Pages.

Podcast episodes and transcripts are governed in Cloudflare R2 and rendered through same-origin Pages Functions. Weekly blog publications are published by AIMS to R2; this repository owns the public blog shell/runtime renderer rather than a second committed article store. Do not create static duplicate snapshots to bypass those source boundaries.

### Cloudflare Pages and Pages Functions

`wrangler.toml` declares the Pages project, R2 bindings, CogniPal Durable Object binding and Agent Readiness service binding. Pages publishes the repository root (`.`) after `bash build.sh` succeeds.

`functions/` contains same-origin runtime routes for blog, podcast/transcript rendering, crawler aliases, the featured-book API, CogniPal gateway routes and Agent Readiness proxying/injection. Shared security and rendering helpers live under `functions/_shared/`.

### CogniPal

Public pages use the first-party CogniPal integration. Same-origin `/api/cognipal/*` Pages Functions validate browser requests and sign server-to-server requests into AIMS Comms Hub. `workers/cognipal-rate-limit/` provides the Durable Object rate limiter used by those routes.

Required Pages configuration includes:

- `AIMS_COMMS_HUB_BASE_URL` — non-secret AIMS Comms Hub origin.
- `COMMS_HUB_COGINPAL_WEBHOOK_SECRET` — Pages secret matching AIMS.
- `COGNIPAL_RATE_LIMITER` — Durable Object binding to the `cognipal-rate-limit` Worker.
- optional `AIMS_COMMS_HUB_CHAT_TIMEOUT_MS` — gateway timeout override.

BotSailor is intentionally absent from the runtime and CSP. `scripts/check_webchat_contract.py` guards against its reintroduction.

### Agent Readiness

`workers/agent-readiness/` is an independently deployed Worker. Pages reaches it through the `AGENT_READINESS` service binding and exposes the public discovery endpoints. The Worker persists its Ed25519 signing key in the `AGENT_READINESS_STATE` Durable Object and does not own a wildcard route on the main website domain.

See `workers/agent-readiness/README.md` and `docs/AGENT-READINESS-DEPLOYMENT.md` for the deployment order and live verification contract.

### JavaScript and third-party governance

Browser JavaScript is kept under repository control and is checked by the build for governed third-party usage, executable inline-script CSP hashes, shared chrome behaviour and size/layout contracts. Any new third-party dependency must also be reconciled with `docs/third-party-dependency-matrix.md` and the CSP in `_headers`.

## Prerequisites

CI uses:

- **Python 3.13**
- **Node.js 22**
- `pip`
- a POSIX shell for `build.sh`
- network access for a full governed build because manuscript PDFs and dependency metadata/packages may be remote inputs

Cloudflare deployment/verification additionally requires the appropriate Cloudflare project, Worker, R2 and Durable Object configuration. Wrangler is only required when manually deploying or verifying the standalone Workers.

Install the exact production dependencies:

```bash
python scripts/check_requirements_lock.py
python -m pip install --disable-pip-version-check --require-hashes -r requirements.txt
python -m pip check
```

`requirements.in` contains the four human-maintained direct production pins. `requirements.txt` is the reviewed, fully resolved production closure and every permitted artefact is bound to a repository-controlled SHA-256 hash. Production installs must use `--require-hashes`; do not bypass that flag or loosen the pins merely to make an upgrade pass. When a direct or transitive dependency changes, update the lock and `scripts/check_requirements_lock.py` together from verified package artefacts.

## Canonical governed build

From the repository root:

```bash
bash build.sh
```

`build.sh` first validates the reviewed dependency closure and hash format, proves pip fails closed against a deliberately mismatched local artefact, then validates the exact installed production dependency versions. If installation is required it installs `requirements.txt` with `--require-hashes`. It then selects the canonical workbook when `EBOOK_WORKBOOK_PATH` is not explicitly set and runs the governed release pipeline.

The pipeline includes:

1. health, repository-hygiene and committed-secret checks;
2. PDF generation/extraction regression tests;
3. Agent Readiness, Pages integration and CogniPal rate-limit tests;
4. workbook import and manuscript manifest generation;
5. genuine manuscript PDF download/extraction for advertised sample chapters;
6. canonical eBook, bundle, growth, social metadata and downloadable PDF generation;
7. redirect, crawler, transcript, shared chrome, image, CSS, colour and third-party-script checks;
8. CogniPal, Pages routing, CSP and schema/growth gates;
9. release validation and generated-output drift rejection outside Cloudflare Pages builds.

The deployable Pages output directory is the repository root (`.`). Build-time manuscript manifests and extraction caches are removed after the pipeline, including on failure.

For local diagnostics only, manuscript download can be skipped:

```bash
bash build.sh --skip-manuscript-sync
```

That mode is **not** equivalent to a release-ready governed build.

## PDF pipeline

Two production dependencies have explicit PDF responsibilities:

- `pypdf` reads manuscript PDFs and extracts genuine chapter samples in `scripts/sync_manuscript_samples.py`.
- `reportlab` generates the deterministic AI glossary download in `scripts/generate_ai_glossary_pdf.py`.

Run the focused cross-library regression test with:

```bash
python -m unittest scripts.test_pdf_pipeline
```

The test generates the glossary twice and requires byte-for-byte deterministic output, then reads the result with pypdf. It also generates a representative ReportLab manuscript fixture and sends it through the real manuscript chapter-extraction function.

When upgrading either PDF dependency:

1. review the upstream release notes and security changes;
2. change **one dependency at a time**;
3. install the exact candidate pin in a clean Python 3.13 environment;
4. run `python -m unittest scripts.test_pdf_pipeline scripts.test_sync_manuscript_samples`;
5. run `bash build.sh` in a connected clean checkout;
6. compare deterministic generated PDF artefacts before/after where applicable;
7. run the dependency vulnerability scan shown below;
8. only then upgrade the second PDF dependency.

The glossary generator uses ReportLab core fonts and no remote images, so it does not require a packaged custom font or remote-image trusted-host configuration.

## Testing and security commands

The canonical build is authoritative, but focused checks are useful during development:

```bash
# Health, hygiene and secrets
python scripts/check_health_contract.py
python scripts/check_repository_hygiene.py
python scripts/scan_secrets.py

# PDF compatibility
python -m unittest scripts.test_pdf_pipeline scripts.test_sync_manuscript_samples

# Agent Readiness / Pages / CogniPal
node --test workers/agent-readiness/test.mjs
node --test scripts/agent-readiness-pages.test.mjs
node --test scripts/pages-routing.test.mjs
node --test scripts/cognipal-rate-limit.test.mjs

# CSP and first-party webchat contracts
python scripts/check_csp_inline_scripts.py
python scripts/check_webchat_contract.py

# Python regression suite
python -m unittest discover -v

# Dependency vulnerability scan used by production-readiness CI
python -m pip install --disable-pip-version-check pip-audit==2.10.1
python -m pip_audit -r requirements.txt
```

Do not treat historical test counts as a release contract. The commands and CI workflows are authoritative as tests are added or removed.

Security controls also include repository secret scanning, CSP/security headers, strict third-party script governance, input/output validation in Pages Functions, bounded CogniPal request bodies/rate limiting, and automated dependency monitoring. See `SECURITY.md` for the repository security policy.

## Deployment

### Cloudflare Pages

The Pages project must remain configured consistently with `wrangler.toml`:

- build command: `bash build.sh`
- output directory: `.`
- R2 bindings: `TRANSCRIPTS_BUCKET`, `BLOG_BUCKET`, `BLOG_IMAGES_BUCKET`
- Durable Object binding: `COGNIPAL_RATE_LIMITER`
- service binding: `AGENT_READINESS` → `agent-readiness`
- CogniPal variables/secrets described above

The standalone Workers must exist before a Pages deployment that depends on their bindings. Follow the deployment order documented in `workers/agent-readiness/README.md` and `docs/cognipal-webchat-deployment.md`.

### Post-deploy validation

The `ebook-subsystem-ci.yml` workflow waits for the expected production release and performs strict live validation. Representative manual checks are documented in `docs/OPERATIONS.md` and include the health contract, home page, eBook catalogue/detail route, machine-readable APIs, crawler files and redirects.

### Rollback

Rollback by selecting a prior Cloudflare Pages deployment or reverting the offending commit, then rerun the exact-SHA/live validation gates. Worker-specific rollback/redeployment procedures are documented with their respective Worker deployment guides.

## Security and content handling

- Never commit API keys, webhook secrets or Cloudflare credentials. Use GitHub/Cloudflare encrypted secret stores.
- Keep CSP changes tied to an explicitly documented dependency or integration.
- Preserve escaping/sanitisation when handling external blog/feed/runtime content; do not insert remote HTML directly into browser output without the existing governance path.
- Keep manuscript/PDF processing bounded by the existing extraction logic and fail on unreadable or insufficient samples rather than publishing fabricated content.
- Run `scripts/scan_secrets.py` and the dependency audit before release-affecting dependency changes.
